## 0. 한 줄 결론

**기술 기반은 A팀(우리) 단일 빌드로 고정하고, B팀의 번역·감수·도트 그래픽을 데이터로 흡수한다.**

## 2. B팀 파일 분석 결과 (4개)

다운로드 폴더에서 받은 파일을 `temp/bteam/`로 복사해 분석함.

### 2-1. `kor.tbl` (96KB, UTF-16LE) — 코드 테이블
- 표준 **SJIS + ASCII** 테이블 위에 한글을 얹은 형태.
- **한글 2351자를 코드 `0xF000–0xF92E`에 순차 매핑** (F000=가, F001=각 … F92D=힝). KS X 1001 완성형 순서 = **우리와 동일 집합**.
- 제어코드: `0x00=㉢`(문자열 종료), `0x0A=㉠`, `0x09=㉡`(개행/제어 추정).
- 전각 기호/숫자(`、。．１２３`)를 그대로 SJIS 코드로 유지.
- ⚠ **우리와 코드값만 다름**: 우리는 예약 SJIS 코드(0x8840–0x9369), B는 0xF000대. 음절 집합이 같아 **음절 기준 1:1 재매핑이면 변환 완료**.

### 2-2. `script.txt` / xlsx `대사` 시트 (≈6,400행) — 번역 텍스트
- 포맷: `주소(6자리 hex),길이(10진 바이트),한글텍스트㉢`
  - 예: `F00138,78,　　　수도가 ２개 이상이고、각 군에㉢`
- 내용: **작전룸(튜토리얼)·맵 디자인·플레이 조건/방법·메뉴** 텍스트. B가 집중한 영역과 일치.
- 번역 품질 양호(자연스러운 한국어). 전각 공백 들여쓰기·전각 문장부호 사용(우리는 ASCII 정규화 정책 — 정책 차이 존재).
- 주소 `F00000~`는 B 확장 ROM의 **재배치 문자열 풀**(아래 ROM diff의 0x0EF0000–0x1000000 변경역과 일치).

### 2-3. `translation.xlsx` (1.1MB) — 통합 워크북
- 시트: **`한글폰트`(2560행=폰트 테이블)** + **`대사`(6405행=위 script)** + `Sheet3`(빈).
- 즉 폰트표 + 스크립트를 한 파일에 담은 작업본. sharedStrings 20,064개.

### 2-4. `bteam_rom.gba` (17.8MB) — 확장 ROM
- 원본 16MB(0x1000000) → **17MB(0x1100000), +1MB 확장**. 타이틀 코드 `GBWARS1+2` 동일.
- 원본 대비 **49개 64KB 블록 변경**. 주요 변경역:
  - `0x0020000–0x0030000` (초기 — 포인터/코드 추정)
  - `0x0B20000–0x0B90000`, `0x0DA0000–0x0E20000`(512KB) — 폰트/그래픽 추정
  - `0x0EF0000–0x1000000`(1MB) + 확장 `0x1000000–0x1100000` — **재배치 텍스트 풀 + 폰트 글리프**(F00000 주소대)
- ⚠ 바이너리 직접 병합 금지. 대조·검증용.

## 3. 호환성 핵심 (병합 난이도 판정)

| 요소 | 호환성 | 병합 방법 |
|---|---|---|
| 한글 음절 집합 | ✅ 동일(2350 완성형) | 변환 불필요 |
| 한글 코드값 | ⚠ 다름(F000대 ↔ 예약SJIS) | **음절 기준 1:1 재매핑**(자동) |
| 번역 텍스트 | ✅ `주소,길이,한글` 단순 포맷 | F-코드 → 음절 → 우리 코드 변환 후 override 흡수 |
| 문장부호 정책 | ⚠ B=전각 유지, A=ASCII 정규화 | 흡수 시 우리 정책으로 정규화 |
| 제어코드 | ⚠ B `㉢/㉠/㉡` ↔ A 종료/개행 코드 | 매핑표 1회 작성 |
| ROM/폰트셋 | ❌ 직접 병합 안 함 | 대조용 |

**결론: B의 번역 텍스트는 "F-코드 → 음절 → 우리 예약코드" 변환 스크립트 1개면 우리 빌드에 흡수 가능.** 기술적 장벽 낮음.

## 7. 합류 첫 1~2주 실행 계획

**1주차 — 수령·대조·온보딩**
1. B 자료 즉시 `archive/`에 원본 보관(유실 방지). B ROM은 `temp/`에서만 분석. ✅ (이미 `temp/bteam/`에 확보)
2. **F-코드 → 음절 → 우리 코드 변환 스크립트** 작성 → B script.txt를 우리 주소체계로 매핑.
3. **1편 작전룸·맵디자인부터 우리 번역 vs B 번역 diff 시트** 생성 → 4분류: ①명백한 개선 ②취향 차이 ③슬롯 초과 위험 ④맥락 확인 필요.
4. 우리 통일사전 ↔ B 용어 병합.
5. B + 시놀부님에게 웹 편집기 30분 온보딩.
6. (선결) 번역 단일 권위(override 오버레이) 정리.

**2주차 — 파일럿 병합·규칙 확정**
7. 작전룸 1개 구간 파일럿 병합 → `build_korean_full.py` + fit/용어/띄어쓰기 QA 통과 확인.
8. 같은 구간을 B가 실플레이 검수.
9. 타이틀/첫메뉴 도트: B 포토샵본 vs 우리 파이프라인 **화면 비교** 후 자산별 채택(크기·팔레트·압축 안전성 검증).
10. 파일럿 결과로 말투 가이드·승인자·반려 기준 확정 → 캠페인 단위 반복.

## 8. 리스크 · 완화책

- **번역 권위 이중화** → 합류 전 override 오버레이 단일화. "ROM 데이터에 들어간 문장만 최종" 합의.
- **크레딧** → 역할(기술/번역/감수/그래픽/커뮤니티) 초기 문서화.
- **라이선스/출처** → B 폰트·PSD·외부 도트 출처 확인, 불명 자산 배포 제외(우리 Galmuri는 OFL 안전).
- **커뮤니티 정치**("말·사건 많은 동네") → "폐기" 표현 금지. "기술은 우리 빌드로 통합, 번역·감수 적극 반영"으로 프레이밍. 배포 채널(한식구 vs 독립) 초기 합의.
- **데이터 유실** → 수령 즉시 원본 보관 + 변환본 분리. ✅
- **QA 과신** → 우리 green check도 실화면 보장 아님. fresh-boot 캡처 + ROM 디코드 병행.

## 9. B에게 보낼 메시지 골자

> 현재 저희 쪽은 1·2편 공통으로 한글 렌더링, 2350자 완성형 폰트, 단일 빌드, 패치 배포까지 잡혀 있습니다. 특히 **게임이 매 화 VRAM에 폰트를 올리는 구조지만 저희는 데이터(코드+글리프 주입)만으로 전 화면 한글이 나오게 해서, 화면/챕터별 폰트셋 수작업이 더 이상 필요 없습니다.** 그래서 ROM 기술 기반은 저희 빌드로 통합하는 게 안전해 보입니다.
>
> 보내주신 파일을 봤습니다. 폰트(한글 2350자)는 저희와 **완전히 같은 집합**이라(코드값만 F000대 ↔ 저희 예약코드로 다름) **번역 텍스트는 변환 스크립트 하나로 저희 빌드에 그대로 흡수**됩니다. 작전룸·맵디자인·메뉴 번역과 검수, 타이틀·메뉴 도트, 플레이 중 발견한 맥락 정보가 특히 중요합니다.
>
> 진행은 확장 ROM을 직접 합치기보다, 작업물을 비교 자료로 받아 저희 데이터 포맷에 반영하고 실제 화면에서 재검증하는 방식으로 가고 싶습니다. 우선 작전룸 한 구간만 파일럿으로 합쳐 보겠습니다. 이후엔 git 안 만지셔도 되게 웹 편집기나 스프레드시트로 제안 번역을 주고받는 흐름을 만들겠습니다. 크레딧은 번역/감수/그래픽 기여가 분명히 드러나게 정리하겠습니다.
