## 1. 레포 개요

레트로 게임의 한글(완성형/조합형) 팬 번역 패치를 **초기 조사 → 텍스트 엔진 RE → 폰트·인코딩 설계
→ PoC → 추출/번역/재삽입 → 포인터 재배치·ASM 훅 → 빌드·패치 → 에뮬레이터 검증**까지 전 파이프라인으로
다루는 Claude Code 스킬이다. **방법론만** 담고 ROM/저작 자산은 포함하지 않는다.

- 구조: 단계별 공통 전략(`references/strategy/`, 13종) + 플랫폼별 하드웨어·사례 노트(`references/platforms/`, 8종).
- 모집단: 선행 11개 한글화 프로젝트 전부 **Compile 사의 일본어 원문·텍스트 중심 게임**(마도물어/뿌요뿌요/나조뿌요 계열).
  → "전형/보통"으로 서술된 패턴은 가설로 취급하고 실측 확정하라는 고지가 반복된다.
- 우리와의 직접 관련성: **GBA 플랫폼 문서는 없다.** 그러나 strategy 축(조사 순서·검증 원칙·재삽입·폰트·PoC)은
  플랫폼 불문 공통이며, 카트리지 ROM 2종(SNES 65816 / MD 68000)이 GBA(ARM7TDMI 카트리지 ROM)와 매체·뱅킹·헤더
  체크섬 측면에서 가장 가깝다.

### 핵심 불변식(SKILL.md) — 우리도 따르는 원칙
- 0원칙: **플레이어는 보통 한 번만 플레이** → 깨진 글자/오역/말투붕괴도 전부 블로커.
- 원본 ROM·디스크는 절대 커밋 금지(해시만 문서화). **PoC 통과 전 본 구현 금지. 라운드트립 우선. 인코딩 누락=빌드 에러.**
- 사례 수치(슬롯 수·빈 공간·포인터 폭)는 이식하지 말고 재실측.

## 3. 우리 GBA 프로젝트(일본판 1+2)에 대조 — 이미 함 / 참고할 점 / 차이점

작업 지시가 강조한 4축(reinsertion=포인터재배치, font-strategy, build-and-verify=라운드트립, poc 원칙) 중심.

### 3.1 PoC 원칙 (`poc.md`)

- **이미 함**: 우리는 "한글 1자 출력"을 이미 통과했다. CLAUDE.md 기준 PoC 3건 검증 —
  ① FONT_BASE 주입(대화 글리프 자리에 galmuri 주입 → 인게임 한글), ② 멀티음절, ③ **예약코드→테이블→한글**(0x8AEF→"테").
  레포가 정의한 3대 전제(글리프공간/인코딩공간/렌더경로)를 정확히 우리가 검증한 항목과 일치한다.
- **우리 경로 위치**: 레포의 "단계 3 — 자체 디스패치"가 아니라, 대화 렌더는 **단계 1.5(글리프 슬롯 주입 + 미사용 SJIS 코드 예약)**에 가깝다.
  per-char 글리프 복사 지점(IWRAM 0x03006744)에 galmuri를 주입하므로 ASM 훅 없이 데이터만으로 동작했다(레포 단계1의 "코드 변경 0"에 근접).
  반면 2편 타일맵 렌더러(0x313F8C/0xB11BB0/0xA3C7E4)는 bit15 한글코드를 VRAM 복사하는 **hook = 레포 단계 2~3**에 해당.
- **참고할 점**: poc.md의 "마이크로 PoC로 더 쪼개라"는 원칙은 향후 미발견 화면(전투 UI 등)에서 새 렌더 경로를 만날 때 재적용 가치가 있다.

### 3.2 폰트 전략 (`font-strategy.md`)

- **이미 함**: **완성형** 채택(레포 11종 전부와 동일 결론). 음절 글리프 사전 렌더(galmuri 11×11, 8px 셀, 4bpp).
  번역 실사용 음절만 수집해 빈도/슬롯 매핑(`syllable_to_code_2350.json`, `kor_glyphs_2350.bin`). 2350자 KS X 1001 완성형 additive 확장 완료.
- **이미 함**: 인코딩 공간을 **미사용 SJIS 코드 풀(예약코드 3326개, `data/reserved_codes.json`)** + 한자테이블 확장으로 확보 —
  레포 §2의 "free prefix + index 2바이트" 표준 형태와 정확히 같은 발상.
- **참고할 점 ①**: §2.2 **"단일 파일 분포는 신뢰하지 말고 전 코퍼스 합산으로 prefix 0회 확인"** 교훈.
  우리는 예약코드를 미사용 SJIS에서 뽑았는데, **글리프 사용 통계까지 교차검증**(텍스트뿐 아니라 한자테이블·외자 글리프가 그 코드를 실사용하지 않는지)했는지 재점검할 가치가 있다.
  PC-98 사례처럼 "텍스트엔 0회지만 외자 글리프로 실사용 중"인 코드를 잡으면 화면 깨짐이 난다.
- **참고할 점 ②**: §3 글리프 예산을 "병목 4유형의 min"으로 산정. 우리는 2350자 풀빌드라 인코딩공간·저장용량은 여유.
  다만 **타일 인덱스 폭**(2편 타일맵 bit15 한글코드 범위 0x8840~0x9369 = 약 2345슬롯)이 실질 상한이므로,
  2350자 전수 vs 실사용 음절의 매핑이 이 범위에 들어맞는지(슬롯 상한 대비 잔여)를 빌드 시 계속 모니터링하는 게 레포 권고와 일치.
- **차이점**: 레포 사례는 8×8 같은 극소 셀에서 완성형 vs 조합형 가독성을 고민하지만, 우리는 11×11 셀이라 가독성 이슈가 작다.

### 3.3 재삽입·포인터 재배치 (`reinsertion.md`)

- **이미 함**: UI 라벨은 사실상 **길이 보존**(슬롯 길이 제한, `execute_phase5_4.py`가 코드영역 skip + 슬롯 초과 truncate) —
  레포 §1.1 정책 그대로. 대화 한글은 예약코드+글리프 주입이라 **포인터 재배치가 거의 불필요**한 구조.
- **이미 함**: 2편 타일맵 렌더 3경로 **ASM 훅** = 레포 §4 "트램폴린→디스패치→렌더" 3층 구조의 실사례.
- **참고할 점 ①**: §6.1 **read-ahead 가드** — "현재 +1 바이트를 프리페치해 제어코드 판정하는 코드"를 전수 찾아 한글 2바이트 코드가 오판되지 않게 보호.
  우리 변환루틴(0x08EFE788)·한자테이블 검색 경로에 2바이트 예약코드가 프리페치 오판(조기 flush/종료)을 일으키지 않는지 점검 항목으로 유효.
- **참고할 점 ②**: §6.2 **VRAM/타일 잔류 클리어** — 한글이 원문보다 타일 소비가 커 "이전 대사 글자가 다음 화면에 유출"되는 증상.
  우리도 잔여 overflow 882행(한글>슬롯) 처리 시, 클리어 범위 경계 행/열을 실측 확정하라는 SNES 마도물어 교훈이 직접 적용된다.
- **참고할 점 ③**: §4.4 **"ASM은 raw 바이트가 아니라 명령어로 emit"** — 우리 2편 hook을 헥스 배열로 손코딩했다면,
  명령어 enum/라벨 어셈블러 또는 디코더와 테이블 공유 방식으로 옮기면 분기 오프셋 손계산 버그가 구조적으로 사라진다. 향후 hook 추가/이동 시 권장.
- **참고할 점 ④**: §6.6 **인코딩 누락 = silent skip 금지, 빌드 에러로** — 누락 시 미패치 원문 바이트가 한글 디코더를 통과해 prefix 오감지로 멀리서 깨진다.
  우리 빌드(`build_korean_full.py`)가 매핑 없는 한글 음절을 만나면 **빌드 실패**시키는지 확인할 가치(QA 게이트 강화 포인트).
- **차이점**: 레포 사례 다수는 텍스트가 연속 블록이라 "제자리 성장 + 누적 shift 포인터 보정"이 핵심이지만,
  우리는 예약코드 방식이라 길이 변동을 포인터 재배치 없이 흡수 → 레포의 역순 splice 알고리즘은 우리 메인 경로엔 불필요(UI 일부에만 잠재 적용).

### 3.4 빌드·검증·라운드트립 (`build-and-verify.md`)

- **이미 함**: 단방향 재현 빌드 — `build_korean_full.py`가 **base=원본 ROM에서 매번 처음부터** 재생성(누적 수정 아님). 레포 핵심 원칙과 일치.
- **이미 함**: **BPS 배포**(원본 CRC32 내장으로 오적용 차단) — 레포 §2 카트리지 ROM 1순위 권고와 동일. IPS는 보조.
- **이미 함**: 빌드타임 QA 게이트 다수 — `qa_integrity_map.py`(무결성맵↔ROM), `qa_text_fit.py`(오버플로), `qa_ascii_residuals.py`, `verify_dist_integrity.py`(배포 3중 해시), `phase6_basic_test.py`(부팅/체크섬/한글검출). 레포 §1 "빌드가 곧 1차 QA"와 정합.
- **이미 함**: 에뮬레이터 검증 — mgba 0.10.5 + 헤드리스 디버거(mgbah, loadstate)로 BP/watch/네비. 레포 §4 Lua/MCP 자동화 권고의 우리 버전(mGBA Lua 스크립팅).
- **참고할 점 ①**: §4 **분기/캐릭터 루트별 진입점은 전부 별개 테스트** — SNES 나조뿌요 사례에서 한 루트만 시작 즉시 깨짐.
  우리는 1편/2편 두 게임 + 모드별(캠페인/대전/트라이얼 등) 진입점이 많으므로, 스모크 체크리스트를 모드별로 분리 운용할 가치.
- **참고할 점 ②**: **라운드트립(추출 무수정 재삽입 = 원본 byte-identical)** 을 명시적 테스트로 박는다 — 우리는 폰트 풀빌드가 "기존 byte-identical 호환"이라 했는데,
  추출↔재삽입 라운드트립을 별도 단위 테스트로 고정하면 미래 회귀를 자동 차단(레포 §1 강조).
- **참고할 점 ③**: §3 GBA는 카트리지 ROM이라 CD의 EDC/ECC·ISO9660 메타데이터 절은 **무관**(우리에게 불필요). 헤더 체크섬만 관리하면 됨(이미 처리).
- **차이점**: 레포 중간 포맷 표준은 JSON(`entry_id/file_offset/text/ko`)인데, 우리 메인은 `translation_for_import.csv`(address,japanese,korean,length).
  레포가 권하는 `{br}/{page}` 가독 태그 이스케이프는 우리 대사 편집기(scene_catalog/dialogue_map JSON)와 정합적 — CSV→JSON 중간포맷 정합성은 이미 편집기 쪽에서 충족.

## 4. 종합 — 우리에게 가장 실효성 높은 액션 후보 (참고용, 실행은 별도 판단)

레포와 대조했을 때 우리 현황은 폰트·재배치·QA가 대체로 완료 상태이고, 레포 방법론과 **결론이 거의 수렴**한다.
새로 가져올 가치가 있는 구체 점검 항목만 추리면:

1. **예약코드 prefix를 글리프 사용 통계로 교차검증** — 텍스트 0회뿐 아니라 외자/한자 글리프 실사용 여부까지(font-strategy §2.2).
2. **인코딩 누락 시 빌드 실패 보장 확인** — silent skip이 prefix 오감지·원거리 깨짐을 부른다(reinsertion §6.6 / font §3.2).
3. **read-ahead 가드 점검** — 2바이트 예약코드가 변환루틴/한자테이블 프리페치 판정에 오판되지 않는지(reinsertion §6.1).
4. **잔여 overflow 882행 처리 시 VRAM 잔류 클리어 경계 실측**(reinsertion §6.2).
5. **2편 hook의 ASM을 명령어 emit 방식으로**(헥스 손코딩이면) — 향후 hook 변경 안정화(reinsertion §4.4).
6. **모드별 스모크 체크리스트 + 추출↔재삽입 라운드트립 단위 테스트 고정**(build-and-verify §1, §4).

> 위 6개는 레포가 제시한 "검증된 함정/안전장치" 목록이며, 우리 게임에서 그대로 성립한다는 보장은 없으므로
> (레포 자체 고지대로) 각 항목은 우리 ROM에서 실측해 확정한다.
