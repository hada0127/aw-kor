GBA ROM 한글화 프로젝트의 관점에서 본 작업 내역(`tools/build_korean_full.py`)에 대한 **적대적 엄격 리뷰** 결과입니다. 겉보기에 정상 작동하는 것처럼 보이는 구현 뒤에 숨은 실기 크래시 위험과 꼼수(fragile hack)들을 지적합니다.

### 1. A2 맵선택 공백 훅 (`PART2_HOOK_SPACE_A2CC`)의 실기 얼라인먼트 크래시 위험 (최중요)

*   **동작 분석**: 훅 코드([PART2_HOOK_SPACE_A2CC](file:///Users/tarucy/project/aw-kor/tools/build_korean_full.py#L9967-L9982))는 반각 공백(`0x20`, 1B)을 만나면 문자열 포인터 `r4`를 `subs r4, #1`로 강제 감소시킨 뒤 복귀하여, 본체 루프 끝의 `r4 += 2`와 연쇄 작용으로 결과적으로 `+1`만 증가하게 만듭니다.
*   **하드웨어 결함(Alignment Fault)**: 
    *   공백 1바이트가 소비된 순간 이후부터 `r4` 문자열 포인터는 **홀수 주소(Odd Address)**를 가리키게 됩니다.
    *   GBA의 ARM7TDMI 아키텍처는 홀수 주소에서 하프워드/워드 단위 정렬 접근(`ldrh`/`ldr`)을 실행할 경우, 하드웨어 수준에서 **비트 회전(Rotation)을 일으켜 완전히 오염된 데이터를 반환**하거나 오동작을 일으킵니다.
    *   파서 루프가 `r4`를 통해 문자를 읽어올 때 바이트 단위(`ldrb`)로만 처리하는지 엄격히 검증되었습니까? 만약 루프 본체나 호출 함수 내부에서 `ldrh`로 문자열을 참조하는 코드가 단 하나라도 존재한다면, 에뮬레이터(mGBA 등)는 이를 관대하게 처리하여 정상 작동하는 것처럼 보일지 몰라도 **실기(GBA/NDS/GBA Micro 등)에서는 글자가 무작위 한자로 깨지거나 크래시**가 납니다.
    *   **대안**: 렌더러가 홀수 정렬 상태의 포인터를 다루게 만드는 임시방편(r4-1 트릭) 대신, 맵 이름 데이터를 로드하는 로더 레벨에서 1바이트 공백을 감지해 강제로 2바이트 전각 공백(`0x8140`)으로 치환한 임시 버퍼를 렌더러에 넘겨주는 방식이 훨씬 안전합니다.

### 2. A1 CO 이름 OBJ 패치 (`patch_part2_domino_co_name_obj`)의 중복 렌더링 및 낭비

*   **코드 결함**: [CO_NAME_KO](file:///Users/tarucy/project/aw-kor/tools/build_korean_full.py#L8695-L8700)에 `'도미노'`가 중복 정의되어 있습니다. 
*   **구조적 취약성**:
    *   1편과 2편의 도미노 이름 OBJ가 물리적으로 분리되어 있어 두 번 덮어쓴 것으로 보이나, 이는 리포인팅(Repointing)을 회피하고 raw OBJ 덮어쓰기에 의존하는 꼼수입니다.
    *   동일한 텍스트를 중복 렌더링하면, 향후 글자 가중치(Font weight)나 텍스트 길이를 수정할 때 두 슬롯 중 하나의 LZ77 압축 결과가 원본 크기(`consumed`)를 초과하여 빌드가 깨질(`AssertionError`) 위험도가 2배로 증가합니다.
    *   **대안**: CO 테이블(`0x081BE68`, stride `0x44`) 내에서 1편과 2편의 도미노 이름 OBJ 포인터를 동일한 롬 주소로 리포인팅하여 단 한 번만 렌더링하도록 일원화해야 합니다.

### 3. A3 룰 요약 값 렌더러 (`_render_value_obj`)의 텍스트 잘림(Clipping) 검증 누락

*   **동작 분석**: Galmuri7 폰트를 사용해 8px 높이의 타일 너비(`n_tiles * 8` 픽셀)에 맞춰 가운데 정렬 렌더링을 수행합니다.
*   **결함**: 
    *   계산된 텍스트 전체 너비 `tw`가 지정된 영역 너비 `width`보다 클 경우, 우측 영역을 벗어나는 픽셀들을 단순히 버리는 클리핑 조건(`if 0 <= px < width`)만 설정되어 있습니다.
    *   만약 번역 문자가 늘어나거나 폰트 폭이 임계점을 초과하더라도 빌드 스크립트는 아무런 경고나 예외 없이 **우측 글자가 뚝 잘려나간 롬을 그대로 빌드**합니다.
    *   **대안**: `_render_value_obj` 내에 `assert tw <= width, f"Value text '{korean}' overflows boundary ({tw}px > {width}px)"` 검증식을 즉각 추가해야 합니다.

### 4. B팀 텍스트 보호의 허구성 (렌더러-데이터 긴밀 결합)

*   **개념적 결함**: `dialogue_overrides.json`을 수정하지 않아 번역 수치상 `qa_bteam_drift`가 0인 것은 일종의 눈속임입니다.
*   **결과**:
    *   번역 텍스트에 들어있는 특정 바이트 패턴(`0x20`)에 끼워 맞추기 위해 엔진의 렌더러 루프 코드를 런타임 하드코딩 수준으로 개조했습니다.
    *   이는 데이터와 렌더러 로직 간의 결합도를 높여, 향후 텍스트 포맷이나 다른 번역 데이터에서 `0x20`을 다른 용도로 제어할 때 예기치 않은 부작용을 낳을 수 있는 기술 부채입니다.

### 5. A3 룰 요약 HUD 타일 raw 영역 오염 검증 누락

*   **위험 요인**: 
    *   `patch_part2_campaign_rule_summary_labels` 및 `patch_part2_campaign_rule_value_labels`에서 `0x45D334~0x45D934`, `0x45DA34~0x45DC74` 영역을 덮어씁니다.
    *   이 주소들이 룰 요약 HUD 전용인지, 아니면 ROM 내의 타 그래픽 리소스나 UI가 이 스프라이트 타일 영역을 공유(Shared Tileset)하고 있는지 완벽한 cross-reference가 확보되었습니까?
    *   만약 해당 주소의 타일이 게임 내 다른 화면(예: 캠페인 맵의 다른 메뉴, 미션 클리어 연출 등)에서 공유되고 있다면, 룰 요약 화면에서는 정상으로 보여도 **다른 씬 진입 시 그래픽이 산산조각 나 깨지는 회귀(Regression) 현상**이 일어납니다. VRAM dump 및 단일 OAM trace만으로 green check를 주기에는 검증 범위가 너무 협소합니다.
